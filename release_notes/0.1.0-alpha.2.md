# scry 0.1.0-alpha.2

A small, host-facing release. The engine reads exactly what it read before; what
changed is how much the stream **tells you about the profile that won**.

## The attach now names the contract

A host pointed at a folder of profiles doesn't choose which one attaches — the
target's memory does, through the probe test. Until now the stream reported only
the winner's label, which is a human string. It now also reports the file it came
from and the **contract** it declares:

```json
{"event":"attached","scry":"0.1.0-alpha.2","pid":1234,"process":"game.exe",
 "profile":"Example (Steam)","profile_file":"./profiles/1.5.0.json",
 "contract_version":1,"watches":7,"pointer_bits":64}
```

- `profile_file` — which candidate actually claimed the process. With
  `--profiles <dir>` this is the difference between "something attached" and
  knowing what.
- `contract_version` — the profile's optional `contractVersion`, or `null` when
  it declares none.

Both are additive; a reader that ignores unknown keys is unaffected.

## `contractVersion` in the profile format

A profile may now carry `"contractVersion": 1` next to `label`. It versions the
**shape** of what the profile emits — which watches, of which types — and is
orthogonal to `match.version`, which pins the *build* the offsets were authored
against:

```text
build 1.4.2 -> profile 1.4.2 -\
build 1.5.0 -> profile 1.5.0 --+-> contract 1
build 2.0.0 -> profile 2.0.0 ---> contract 2
```

Offsets move on nearly every patch; names outlive them. Keeping the two apart
means the common case — a patch that shifts addresses without changing the data —
costs one new profile on the same contract, and whatever renders `hp` and `party`
downstream never has to be touched. Bump the contract only when a watch is
renamed, retyped, added, or removed.

**The engine never reads this field.** It parses it, carries it, and hands it back
on `attached`. Acting on it would mean forming an opinion about what a value
*means*, which is the line this engine doesn't cross — the field exists for
catalogues and for whoever draws the values on screen.

`il2cpp2scry` passes a map's `contractVersion` through to the profile it emits,
so a re-conversion against a new game dump keeps the contract you declared.

Existing profiles are unaffected: the field is optional, absent stays absent, and
a profile without one round-trips byte-for-byte as before.

| `SHA256SUMS` | pin the download by hash |

Profiles are **not** here, deliberately: a game patch means a new profile, not a
new engine, and bundling them would tie one cadence to the other.

## Known limits

Unchanged from `0.1.0-alpha.1`:

- **Windows is the target.** The Linux backend exists for development and CI.
  On Linux, Yama's default `ptrace_scope=1` also means a host cannot read a game
  that is not its own descendant without `CAP_SYS_PTRACE`.
- **64-bit reader, 32-bit game is unproven.** CI proves 64→64 and 32→32. The
  mixed case (a 64-bit host reading a WOW64 game) has not been exercised.
- **The binaries are unsigned**, so SmartScreen will report an unknown publisher.
- **Nothing is stable yet.** Alpha means the JSON events, the profile schema, and
  the CLI flags may all still change.
