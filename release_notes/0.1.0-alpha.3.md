# scry 0.1.0-alpha.3

One new watch tier, and it is the first one that reads no memory at all.

## `derived` — the numbers the game computes instead of storing

Games routinely **compute** what a player sees rather than keeping it in a field:
percent of max, a party total, an effective stat that is base plus equipment, a
count of living enemies. The arithmetic is trivial; the plumbing to reach the
inputs is not — so until now every consumer of the stream re-implemented it.

A `derived` watch folds values **other watches already produced**, using a small
expression carried as data — the same discipline that makes `collection` express
iteration as `count`/`stride`/`element` rather than as a script:

```json
{ "tier": "derived", "name": "hp_percent", "type": "f32",
  "value": { "mul": [ { "const": 100 },
                      { "div": [ { "watch": "hp" }, { "watch": "hp_max" } ] } ] } }
```

The nodes: `const`, `watch` (optionally with `index` / `field`), `item` under
`each`, the n-ary `add`/`mul`/`min`/`max`, the binary `sub`/`div`, and the folds
`sum`/`count`/`min`/`max` over a list watch with optional `field`, `take` and a
flat `where`. `min`/`max` accept either shape — an array is n-ary over operands,
an object is a fold over a list — because the two JSON types can never collide.

`where` matters more than it looks: heterogeneous lists are the norm, and
`sum damage where school == "fire"` is the difference between a number and
adjacent memory reinterpreted as one. Clauses are flat and AND-ed; there is no
`or`, and a profile that needs one is a signal to reconsider the profile.

An optional `each` names a `collection` declared earlier: the expression runs once
per element and the watch emits a list.

## The boundary that keeps it honest

**A derived watch never touches memory.** It reads only the values of other
watches in the current tick. That single rule is what stops the tier from growing
into an embedded interpreter, and it makes the failure story trivial: any
unavailable input yields an unavailable output — a non-finite or out-of-range
result is `unavailable`, never a saturated number a consumer cannot detect as a
lie. `sum` over an empty list is `0` (nothing matched is a real answer); an empty
`min`/`max` is `unavailable`, because there is no neutral element to return
honestly.

It is also what makes the tier **engine-agnostic by construction**. Everything
engine-specific in scry lives in offsets, AOB signatures and string layouts; by
the time a value reaches an expression it is just a number, a string, a list or a
map. The integration suite proves it against the native `#[repr(C)]` cavia rather
than a managed runtime.

Two consequences worth knowing about:

- **No dependency graph.** Every `{"watch": n}` must name a watch declared
  *earlier in the array*, so a cycle is unrepresentable rather than merely
  detected, and evaluation order falls out of declaration order. A forward or
  self reference is rejected at load time, naming both watches.
- **Two phases per tick.** Every due memory watch is sampled first, then every
  due derived watch is evaluated against the result — fresh values for what was
  sampled this tick, latest known for what wasn't. Derived watches never vote on
  the failure streak that triggers a re-attach: they read no memory, so letting
  them count would make a formula error look like a detached process.

`il2cpp2scry` passes a derived watch through verbatim — it carries no offsets, so
it is the one watch kind a game patch cannot invalidate.

Existing profiles are unaffected: this is a new tier, and nothing about
`tier1`, `tier2`, `collection` or `record` changed.

## Known limits

New in this release:

- **A collection element's fields must be scalars**, so a per-entity sub-list
  cannot hang off an element. A profile computing each character's max HP from
  their own level-up list therefore declares one collection per character instead
  of one `each` over the roster. Allowing a collection field to be a collection,
  recursively with a depth cap, would collapse those — but that relaxes the "one
  shallow level of structure" doctrine, so it is a separate decision.

Unchanged from `0.1.0-alpha.2`:

- **Windows is the target.** The Linux backend exists for development and CI.
  On Linux, Yama's default `ptrace_scope=1` also means a host cannot read a game
  that is not its own descendant without `CAP_SYS_PTRACE`.
- **64-bit reader, 32-bit game is unproven.** CI proves 64→64 and 32→32. The
  mixed case (a 64-bit host reading a WOW64 game) has not been exercised.
- **The binaries are unsigned**, so SmartScreen will report an unknown publisher.
- **Nothing is stable yet.** Alpha means the JSON events, the profile schema, and
  the CLI flags may all still change.
