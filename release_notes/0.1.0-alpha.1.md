# scry 0.1.0-alpha.1

The first published build. An **alpha**: the engine has been proven end-to-end
against real processes in CI, but nothing has consumed it as a released artifact
yet, and the wire format is young enough to still move. Pin the hash, expect to
re-pin.

## What this is for

A host application drives `scry.exe` as a **subprocess** and reads its stdout.
That is the integration shape — not a library to link, not a DLL to load into
your own address space. A profile is community data of uncertain quality; when
it is wrong, the failure lands in a process you can restart, not in yours.

```sh
scry watch --process game.exe --profiles ./profiles/ --format json
```

```json
{"event":"attached","scry":"0.1.0-alpha.1","pid":1234,"process":"game.exe","profile":"Example (Steam)","watches":7,"pointer_bits":64}
{"event":"values","t_ms":0,"values":{"hp":2000,"party":["VALERE","ZALE","GARL"]}}
{"event":"values","t_ms":312,"values":{"hp":1840}}
```

One JSON object per line, flushed per tick; diagnostics stay on stderr, so
stdout parses whole. Readings are **untagged** — a number is a number, a list an
array, a record an object, and a watch that could not be read is `null` — because
the profile already declares each watch's type. Only what *changed* is sent; the
first `values` event carries everything readable. A key being absent means
"unchanged", which is a different claim from `null`, "went dark".

**Ignore event types you do not recognise.** That is the compatibility promise:
new event kinds can appear without breaking a reader that follows this rule.

| `SHA256SUMS` | pin the download by hash |

Profiles are **not** here, deliberately: a game patch means a new profile, not a
new engine, and bundling them would tie one cadence to the other.

Check the binary works on your machine before pointing it at anything:
`scry selftest` spawns the bundled cavia and exercises the whole read path —
module base, pointer chain, AOB scan, RIP-relative decode.

## Known limits

- **Windows is the target.** The Linux backend exists for development and CI.
  On Linux, Yama's default `ptrace_scope=1` also means a host cannot read a game
  that is not its own descendant without `CAP_SYS_PTRACE`.
- **64-bit reader, 32-bit game is unproven.** CI proves 64→64 and 32→32. The
  mixed case (a 64-bit host reading a WOW64 game) has not been exercised, and
  pointer width in chain-walking is the open question there.
- **The binaries are unsigned**, so SmartScreen will report an unknown publisher.
- **Nothing is stable yet.** Alpha means the JSON events, the profile schema, and
  the CLI flags may all still change.
